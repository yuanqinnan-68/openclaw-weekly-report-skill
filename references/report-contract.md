# 周报输出契约

## 输入和输出

输入是飞书周报表中的逐行记录，至少包含任务、负责人、周期、项目、状态、本周进展、风险和下周计划。输出包括顶部指标、本周亮点、风险预警、逐项目任务表和下周重点。

## 行级完整性

项目详情必须保持一条输入记录对应一条展示记录。即使任务名称、负责人、项目、周期和内容完全相同，也不判断重复、不合并、不删除。空内容保持空字符串。

AI 返回结果必须以稳定的行 ID 对齐输入。只接受当前批次中存在的 ID；模型漏回某个 ID 时，该行使用原文兜底。不能让模型自由决定输出条数。

## 文本提炼

- `task_name`：去掉冗余，建议 8–30 字，不改变任务含义。
- `progress`：只说明本周完成了什么和结果，建议 20–50 字，最多一句。
- `next_plan`：只说明下一步做什么，建议 15–40 字，最多一句。
- 空字段必须输出空字符串。
- 删除过程步骤、重复背景、过多参数和编号，但保留关键名称、数字、版本和结果。
- 禁止省略号、硬截断、虚构结果以及输出输入中不存在的事实。

## 本周亮点

候选只来自本周”已完成”任务。根据进展的信息量选择最多 5 条，每条独立生成一句约 30–60 字的介绍，并按 `1.` 至 `5.` 展示。亮点应包含项目、关键动作和结果，不逐字照抄过程清单。

## 成员贡献总结

紧接在本周亮点之后展示。按成员聚合本周内容（不含下周规划），每人生成一句约 20–40 字的中文总结，只说做了什么和关键结果。空字段保持空字符串，不臆造内容。每位成员对应输出中的一个 `OwnerSummary` 对象，字段为 `owner` 和 `summary`。

## 状态分类与排序

状态标签及固定顺序：

1. `done`：已完成
2. `stuck`：卡住
3. `debug`：调试中
4. `docking`：对接中
5. `design`：设计中
6. `doing`：推进中、开发中等进行态
7. `todo`：待开始或其他未识别状态

排序必须稳定：只改变不同状态之间的先后，同状态的原始行顺序不变。

## 验证清单

- 项目详情总行数与输入记录数一致。
- 每个输入 ID 在输出中恰好出现一次。
- 空字段仍为空。
- 亮点不超过 5 条，且均来自已完成任务。
- 成员贡献总结中每位出现在本周内容中的成员恰好有一条记录。
- 所有项目表使用统一状态顺序。
- 没有省略号、断句、JSON 残片或 Markdown 围栏。
- HTML 对长句自动换行，不能用固定高度或隐藏溢出来截断内容。
